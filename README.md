# Рядом — журнал здоровья

Лабораторные работы № 1 «Интерфейс приложения и каркас frontend» и № 2 «Backend, API и работа с базой данных».

Первая работа — интерфейс на React с демоданными. Вторая — отдельный API на FastAPI с PostgreSQL и SQLAlchemy. Инструкция для второй работы находится в разделе [«Лабораторная № 2»](#лабораторная--2). Frontend пока работает с демоданными в памяти; подключение его к API в этом этапе не выполнено. API можно использовать через Swagger UI.

Приложение для домашнего медицинского мониторинга: пользователь вручную записывает пульс, артериальное давление, температуру, сахар крови и вес. На главной видны последние измерения, в истории — все записи. Приложение ведёт журнал и не ставит диагнозы, не даёт медицинских рекомендаций и не оценивает опасность показателей.

## Что можно сделать

- Посмотреть значение, единицу измерения и дату последней записи каждого типа.
- Открыть всю историю и отфильтровать её по показателю.
- Добавить измерение с датой, временем и необязательной заметкой.
- Ввести верхнее и нижнее давление отдельно.
- Получить сообщение об ошибке ввода или уведомление об успешном сохранении.

## Технологии и окружение

Frontend: React 19, TypeScript 5, Vite 7, React Router 7, Material UI 7 и Emotion. Используются функциональные компоненты, стандартные `useState` и `useEffect`, передача данных через props. Redux не используется. Backend второй работы описан ниже.

Нужны Node.js **22.12 или новее** и npm. Работу проверяли с Node.js 24.19.0 и npm 11.9.0. Для первоначальной установки зависимостей нужен доступ к npm registry. После установки интерфейс не загружает внешние шрифты, изображения или данные.

## Данные и ограничения хранения frontend

При запуске создаются десять демонстрационных записей одного условного пользователя. Они не содержат настоящих персональных сведений; даты рассчитываются относительно момента открытия приложения.

Измерения, добавленные через frontend, хранятся **только в памяти React**, в `useState` компонента `App`. После перезагрузки страницы они исчезают и снова появляются исходные демонстрационные данные. `localStorage`, аккаунты и интеграция с устройствами не используются. Записи, добавленные через API второй работы, хранятся отдельно в PostgreSQL и сохраняются после перезапуска.

Числа хранятся числами. У давления отдельные поля `systolic` и `diastolic`; у остальных типов — `value`. Дата хранится строкой ISO, а отображается в местном времени устройства. Для температуры, сахара и веса можно вводить дроби через точку или запятую. Пульс и обе части давления должны быть целыми. Значения должны быть положительными и конечными. Проверяется также обязательность и корректность даты. Произвольные медицинские диапазоны не задаются. Заметка необязательна и ограничена 500 символами.

## Простое объяснение для защиты

1. **Где хранятся записи.** `App` создаёт массив измерений с помощью `useState(createDemoMeasurements)`. Он расположен выше страниц, поэтому переходы между ними не сбрасывают массив.
2. **Как сохраняется запись.** Поля формы имеют своё локальное состояние. При нажатии «Сохранить» форма проверяет ввод, переводит текстовые значения в числа и вызывает переданную из `App` функцию `onAdd`. В `App` запись получает уникальный `id` и добавляется в новый массив через `setMeasurements`. Затем React Router открывает историю, а `Snackbar` показывает уведомление.
3. **Как история получает данные.** `App` передаёт актуальный массив через props в `HistoryPage`. Страница делает отсортированную копию массива и оставляет выбранный тип. Исходный массив не изменяется. Общий компонент `MeasurementList` выводит записи или сообщение, что записей нет.
4. **Как обновляются карточки.** Главная получает тот же массив. После изменения состояния React перерисовывает её. Для каждого типа главная берёт первую запись из массива, отсортированного по дате измерения. Поэтому добавление старой записи в историю не заменяет более свежий показатель на главной.
5. **Как устроены переходы.** `BrowserRouter` следит за адресом, `Routes` выбирает страницу, `Link` и `NavLink` меняют маршрут без перезагрузки документа. После сохранения используется `useNavigate`. Маршрут `*` показывает 404.
6. **Зачем нужны технологии.** React строит интерфейс из компонентов и обновляет его при изменении состояния. TypeScript проверяет типы и помогает не перепутать обычное измерение с давлением. Vite запускает сервер разработки и собирает production-файлы. React Router связывает страницы с адресами. Material UI даёт готовые поля, кнопки, таблицы, уведомления и общую тему.

## Лабораторная № 2

Backend принимает HTTP-запросы, проверяет поля и сохраняет профили и измерения в PostgreSQL через SQLAlchemy. Используется обычный синхронный код: функции маршрутов вызывают функции из `crud.py`, а те работают с сессией БД. Python нужен версии **3.10 или новее**; проверено на Python 3.12 и PostgreSQL 17. Зависимости перечислены в `backend/requirements.txt`.

### Структура backend

```text
backend/
  .env.example          пример настроек без настоящих секретов
  requirements.txt      зависимости приложения
  requirements-dev.txt  дополнительные зависимости тестов
  app/
    main.py             создание FastAPI, подключение маршрутов, ошибки валидации
    config.py           чтение настроек из окружения и backend/.env
    database.py         engine, сессия БД и общая Base для моделей
    models.py           таблицы SQLAlchemy, связи и ограничения БД
    schemas.py          Pydantic-схемы запросов и ответов
    crud.py             создание, чтение, изменение и удаление данных
    init_db.py          создание таблиц
    routers/
      profiles.py       HTTP-маршруты профилей
      measurements.py   HTTP-маршруты измерений
  tests/                проверки API на отдельной PostgreSQL БД
compose.yaml            локальная PostgreSQL и постоянный том данных
```

### Модель данных

Связь: **один профиль → много измерений**. Профиль здесь — имя владельца журнала, а не аккаунт с паролем. Авторизации в этой работе нет, API рассчитан на локальную учебную проверку.

| Таблица | Поля |
| --- | --- |
| `profiles` | `id` — целочисленный первичный ключ; `name` — непустое имя до 100 символов; `created_at` — дата создания с часовым поясом, задаётся БД |
| `measurements` | `id` — целочисленный первичный ключ; `profile_id` — внешний ключ на `profiles.id`; `type` — тип показателя; `measured_at` — время измерения с часовым поясом; `value` — одно числовое значение; `systolic` и `diastolic` — целые значения давления; `note` — заметка до 500 символов |

У давления `value = null`, а `systolic` и `diastolic` заполнены. У остальных показателей заполнено `value`, а поля давления равны `null`. Типы и единицы совпадают с первой работой: `pulse` (уд/мин), `pressure` (мм рт. ст.), `temperature` (°C), `sugar` (ммоль/л), `weight` (кг). Единица определяется типом и отдельно не хранится.

PostgreSQL проверяет внешний ключ, допустимый тип, набор полей, положительность и конечность значений, целочисленность пульса. На `profile_id` и `measured_at` есть индексы. Профиль с измерениями удалить нельзя: API вернёт `409`. Сначала нужно явно удалить его измерения. Имена профилей могут совпадать.

### 1. Настроить окружение

Откройте терминал **в корне проекта**, где находятся `package.json` и `compose.yaml`. Для варианта ниже установите Docker с Compose; в Windows подойдёт запущенный Docker Desktop.

Скопируйте пример настроек:

```bash
# macOS / Linux
cp backend/.env.example backend/.env
```

```powershell
# Windows PowerShell
Copy-Item backend/.env.example backend/.env
```

Откройте `backend/.env` и замените `change_me_local` своим локальным паролем **в двух местах**: `POSTGRES_PASSWORD` и `DATABASE_URL`. Для учебного запуска удобно взять пароль из латинских букв и цифр; специальные символы в части пароля URL требуют URL-кодирования.

| Настройка | Назначение |
| --- | --- |
| `POSTGRES_DB` | Имя создаваемой Docker-контейнером базы, по умолчанию `ryadom` |
| `POSTGRES_USER` | Пользователь PostgreSQL, по умолчанию `ryadom` |
| `POSTGRES_PASSWORD` | Пароль этого пользователя |
| `DATABASE_URL` | Строка SQLAlchemy: `postgresql+psycopg://пользователь:пароль@localhost:5432/имя_базы` |

FastAPI читает `DATABASE_URL`; остальные переменные нужны контейнеру PostgreSQL. Переменные окружения имеют приоритет над `.env`. Настоящий `.env` исключён из Git, а `.env.example` можно хранить в репозитории.

### 2. Запустить PostgreSQL

Из корня проекта:

```bash
docker compose up -d --wait db
docker compose ps
```

Контейнер должен иметь состояние `healthy`. База `ryadom` создаётся автоматически при первом запуске. Данные лежат в Docker-томе `postgres_data` и сохраняются после остановки контейнера. Порт БД открыт только на `127.0.0.1:5432`.

Если PostgreSQL уже установлен на компьютере, Docker необязателен. В pgAdmin или `psql` создайте пользователя и БД (подставьте собственный пароль):

```sql
CREATE USER ryadom WITH PASSWORD 'your_local_password';
CREATE DATABASE ryadom OWNER ryadom;
```

Затем укажите подключение к этой БД в `backend/.env`. Встроенной замены PostgreSQL на SQLite нет.

### 3. Установить backend и создать таблицы

Перейдите в папку `backend`. Дальнейшие Python-команды выполняются **из этой папки**.

Windows PowerShell:

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m app.init_db
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

macOS / Linux:

```bash
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m app.init_db
.venv/bin/python -m uvicorn app.main:app --reload
```

Активация виртуального окружения не требуется: команды вызывают Python напрямую из `.venv`. В примере сервер слушает `127.0.0.1:8000`. Остановить его можно сочетанием `Ctrl+C`. Для следующего запуска достаточно поднять БД и повторить команду `uvicorn`.

`app.init_db` создаёт таблицы из моделей SQLAlchemy. Повторный запуск не удаляет записи. Это не система миграций: при будущих изменениях существующих столбцов понадобятся отдельные миграции. Сервер сам не создаёт таблицы, поэтому первый запуск `init_db` обязателен.

### 4. Работать с API через Swagger UI

Откройте **http://127.0.0.1:8000/docs**. Для каждого запроса раскройте нужную строку, нажмите **Try it out**, заполните поля и нажмите **Execute**. В ответе видны код HTTP и JSON. Схема OpenAPI также доступна по `/openapi.json`. Стандартный Swagger UI загружает JS и CSS с `cdn.jsdelivr.net`, поэтому для его открытия нужен интернет; сами запросы API работают локально.

1. Создайте профиль: `POST /api/profiles`, тело `{"name": "Учебный профиль"}`. Получите `201` и запомните возвращённый `id`.
2. Создайте измерение: `POST /api/measurements`. Подставьте этот `id` в `profile_id` примеров ниже.
3. Посмотрите записи: `GET /api/measurements`, при необходимости укажите `profile_id` и `type`.
4. Прочитайте одну запись: `GET /api/measurements/{measurement_id}`.
5. Измените её: `PUT /api/measurements/{measurement_id}`, отправив полное новое тело.
6. Проверьте удаление профиля с записью: ожидается `409`. Затем удалите измерение и профиль — оба запроса вернут `204` без тела.

Пример пульса (замените `1` на полученный `id` профиля):

```json
{
  "profile_id": 1,
  "type": "pulse",
  "value": 72,
  "measured_at": "2026-11-08T09:00:00+03:00",
  "note": "После отдыха"
}
```

Пример давления:

```json
{
  "profile_id": 1,
  "type": "pressure",
  "systolic": 120,
  "diastolic": 80,
  "measured_at": "2026-11-08T09:05:00+03:00",
  "note": "Утреннее измерение"
}
```

Для температуры, сахара или веса используйте первое тело с соответствующим `type` и дробным `value`, например `36.6`, `5.1` или `68.4`. В JSON дроби записываются с **точкой**, числа — без кавычек. Поле `note` можно опустить, тогда будет пустая строка.

### Маршруты и ответы

| Метод | Адрес | Действие | Успешный статус |
| --- | --- | --- | --- |
| POST | `/api/profiles` | Создать профиль | 201 |
| GET | `/api/profiles` | Список профилей по возрастанию ID | 200 |
| GET | `/api/profiles/{profile_id}` | Один профиль | 200 |
| PUT | `/api/profiles/{profile_id}` | Заменить имя профиля | 200 |
| DELETE | `/api/profiles/{profile_id}` | Удалить профиль без измерений | 204 |
| POST | `/api/measurements` | Создать измерение | 201 |
| GET | `/api/measurements` | Список измерений от новых к старым | 200 |
| GET | `/api/measurements/{measurement_id}` | Одно измерение | 200 |
| PUT | `/api/measurements/{measurement_id}` | Полностью заменить поля измерения | 200 |
| DELETE | `/api/measurements/{measurement_id}` | Удалить измерение | 204 |

У обоих списков есть `offset` (по умолчанию 0, допустимо 0–2147483647) и `limit` (по умолчанию 100, допустимо 1–100). Для следующей страницы используйте `offset=100`. Измерения можно одновременно фильтровать по `profile_id` и `type`, например `/api/measurements?profile_id=1&type=pulse&limit=20&offset=0`. При одинаковом времени выше находится запись с большим `id`. Пустой результат — `[]`; фильтр по несуществующему профилю возвращает `404`.

`PUT` заменяет всю запись: обязательные поля нужно отправлять заново. Если не передать `note`, заметка станет пустой. При смене давления на другой тип передайте `value`, а поля давления опустите — сервер очистит их. Можно перенести запись в другой существующий профиль, изменив `profile_id`. Идентификатор записи при этом сохраняется. Частичное обновление `PATCH` не реализовано.

| Ошибка | Статус и поведение |
| --- | --- |
| Профиль или измерение не найдены, в запросе указан отсутствующий профиль | `404`, например `{"detail": "Профиль не найден"}` |
| Удаляется профиль с измерениями или нарушено ограничение БД | `409`, понятное сообщение; транзакция откатывается |
| Неправильные поля, тип показателя, дата, ID, фильтр или параметры страницы | `422`, общее сообщение и список полей с причинами |

Валидация требует положительных конечных значений; пульс и обе части давления должны быть целыми. Для давления нужны оба поля, для остальных типов — только `value`. Верхний предел ID и полей давления — `2147483647`, это технический предел PostgreSQL `INTEGER`, а не медицинская норма. Дробные значения хранятся как числа с плавающей точкой. Проверок медицинских диапазонов нет. Нулевой символ `\u0000` в имени и заметке запрещён, поскольку PostgreSQL не сохраняет его в текстовых полях.

Время передаётся в ISO 8601 с часовым поясом (`+03:00` или `Z`). Время без часового пояса и несуществующая дата отклоняются. PostgreSQL хранит момент времени; в ответе он может быть представлен в UTC (`09:00+03:00` и `06:00Z` — один момент). Будущая дата, как и в первой работе, не запрещена.

Пример ошибки для дробного пульса:

```json
{
  "detail": "Проверьте поля запроса",
  "errors": [
    {
      "field": "body",
      "message": "Value error, Пульс должен быть целым положительным числом"
    }
  ]
}
```

Обязательность, типы и ограничения отдельных полей проверяет Pydantic, сочетание числовых полей — `check_values`. Схемы ответов проверяют данные перед выдачей клиенту. SQLAlchemy отправляет изменения в БД при `commit`; при нарушении ограничений вызывается `rollback`.

### Проверить сохранение в PostgreSQL

Создайте профиль и измерение через `/docs`, запомните их ID. Остановите API, запустите его снова и выполните GET по тем же ID: записи должны остаться. Чтобы проверить контейнер БД, из корня проекта выполните `docker compose restart db`, дождитесь готовности через `docker compose ps` и повторите GET.

Посмотреть таблицы напрямую можно из корня проекта:

```bash
docker compose exec db psql -U ryadom -d ryadom
```

Внутри `psql`:

```sql
SELECT id, name, created_at FROM profiles;
SELECT id, profile_id, type, value, systolic, diastolic, measured_at, note
FROM measurements ORDER BY measured_at DESC, id DESC;
```

Команда выхода — `\q`. Если вы изменили имя БД или пользователя в `.env`, подставьте их в команду подключения.

Обычная остановка БД: `docker compose stop db`. Запуск: `docker compose up -d --wait db`. `docker compose down` удаляет контейнер, но сохраняет том. **Ключ `-v` удаляет том вместе с данными**, для обычной остановки он не нужен. Изменение пароля в `.env` не меняет пароль пользователя в уже созданной БД: переменные `POSTGRES_*` применяются при первом создании тома.

### Автоматические тесты

Тесты используют настоящую PostgreSQL и **очищают таблицы в тестовой БД**. Создайте отдельную БД, из корня проекта:

```bash
docker compose exec db createdb -U ryadom ryadom_test
```

Из папки `backend`, macOS / Linux:

```bash
.venv/bin/python -m pip install -r requirements-dev.txt
export TEST_DATABASE_URL='postgresql+psycopg://ryadom:YOUR_PASSWORD@localhost:5432/ryadom_test'
.venv/bin/python -m pytest -q
```

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
$env:TEST_DATABASE_URL = "postgresql+psycopg://ryadom:YOUR_PASSWORD@localhost:5432/ryadom_test"
.\.venv\Scripts\python.exe -m pytest -q
```

Замените `YOUR_PASSWORD` локальным паролем из `.env`. Запущенный Uvicorn для тестов не нужен. Если `TEST_DATABASE_URL` отсутствует или имя БД не оканчивается на `_test`, тесты отказываются запускаться. Это отдельная пустая БД для тестов; не указывайте в этой переменной БД с нужными данными.

Покрыты CRUD обеих сущностей, все пять типов измерений, чтение результата из отдельной SQLAlchemy-сессии, смена типа и владельца записи, фильтры, сортировка, страницы списка, неверный ввод, отсутствующие записи, запрет удаления связанного профиля и ограничения самой PostgreSQL при обходе API. Неудачное обновление оставляет прежнюю запись без изменений.

### Частые проблемы

- `ModuleNotFoundError: app`: выполняйте Python-команды из папки `backend`.
- Ошибка отсутствующего `DATABASE_URL`: создайте `backend/.env` по примеру и проверьте название переменной.
- `Connection refused`: проверьте, что БД запущена, адрес и порт в `DATABASE_URL` верны.
- Порт 5432 занят: используйте уже установленную PostgreSQL или замените левый порт в `compose.yaml`, например на `5433`, и порт в `DATABASE_URL`.
- Ошибка аутентификации PostgreSQL: пароль в URL должен совпадать с паролем пользователя БД; смена `.env` не обновляет существующую БД.
- `relation does not exist`: выполните `python -m app.init_db` через Python из `.venv`.
- `/` на порту 8000 возвращает 404: это сервер API, его страница проверки находится по `/docs`; интерфейс React запускается отдельно через `npm run dev`.
